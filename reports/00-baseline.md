Generated by `npx tsx scripts/confidence-distribution.ts --markdown`, run on

## What this measures, and what it does not

This ingests 15 hand-written RFQs (`scripts/lib/benchRfqs.ts`) covering the input
shapes PRD §5.1 names — pipe-delimited tables, `100x Bracket PN-2041 A36`
shorthand, prose requests, "same as PO 4471 but 400 units", a scanned drawing
with no legible specs, and `100/500/1000` quantity-break requests — against a
corpus built **specifically so that GREEN is reachable**
(`scripts/lib/benchCorpus.ts`): every requested item has 3+ recent comparables at
several quantities, low price dispersion, and materials inside the capability
envelope.

That design is the point. If GREEN is unreachable against a corpus built to reach
it, the gate is broken by construction rather than starved of data.

**This measures structure, not accuracy.** The corpus prices are invented. No
statement about pricing error can be made from this file — that requires a real
shop's export through `scripts/backtest.ts` (K3). It is also not `prisma/seed.ts`;
the seed corpus is never used to validate behaviour.

## GREEN = 0. Why — the mechanism

`evaluateConfidence` requires `!signal.missingSpec` for GREEN
(`src/lib/confidence.ts:41`). `missingSpec()` returns
`!fields.material || !fields.finish` (`src/lib/confidence.ts:55`). No code path
in `src/lib/extract.ts` ever assigns `finish` — the pipe-table branch hard-codes
`finish: undefined` (`src/lib/extract.ts:114`) and no other branch sets it at
all. Therefore `missingSpec` is `true` for every ingested line, and GREEN is
unreachable regardless of input quality or corpus depth.

`buildAssumption` (`src/lib/confidence.ts:96`) meanwhile treats a missing finish
as a routine assumption — "finish is assumed mill / as-fabricated unless
otherwise specified". The gate calls the same condition disqualifying. The two
functions contradict each other, and the gate wins.

## What else the baseline exposes

Beyond the defect above, this run surfaced failures across the 15 shapes:

- **R01, R15 — the pipe-table material regex eats the description.** The
  material matcher (`src/lib/extract.ts:100`) tests for `/plate|tube|.../`, so
  for the row `BP-1218 | Base plate 12x18x0.5 | 50 | A36` it assigns
  `material = "Base plate 12x18x0.5"` — the description cell — and the real
  material `A36` is dropped. The bogus material then fails the capability
  envelope check, forcing RED. A fully-specified line is rejected because the
  parser mislabelled a column. Not in the task list; found here.
- **R05 — `same as PO 4471` cannot resolve.** The extractor's regex consumes the
  `PO` prefix and captures `4471`, but the historical quote is numbered
  `PO-4471`, so `resolveAgainstHistory`'s reference lookup never matches. PRD
  §5.1 requires this case to resolve.
- **R07 — quantity breaks are never priced.** `100/500/1000` produced a single
  line at qty 1 via the catch-all prose fallback.
- **R08 — the conflict is dropped.** The "same as PO 4471 but 400 units" note
  alongside a 25-unit table row was priced at 25 with no conflict surfaced.
- **R09 — a new account gets nothing.** History is filtered to `accountId`, so an
  account with no history has an empty comparable pool: RED with no fallback.
- **R10 — qty 50,000 was priced** from comparables spanning 100–1000, by
  averaging unit prices across quantities.
- **R12 — title-block header fields are ignored.** `Finish:`, `Tolerance:` and
  `REV. C` in the header never reach the line.

Only 17 quote lines were produced from 15 RFQs.

### What changed per RFQ, and why

- **R03, R12, R15** now reach GREEN: finish, tolerance and revision are
  extracted from line text and title-block headers, comparables resolve at the
  requested quantity, and a cost record puts margin above the floor.
- **R01, R15/line 1** are AMBER, not GREEN, on `prior_loss_below_price`: the
  corpus contains a lost BP-1218 quote with a competitor price of $45.00, below
  the $48.60 derived here (Task 4). This is the intended behaviour.
- **R05** now prices. `same as PO 4471` normalises to the stored quote number

- **R07** prices the requested `100/500/1000` breaks independently rather than
  collapsing to a single qty-1 line.
- **R09** (new account) prices from workspace-wide history instead of going RED
  with an empty pool, and states that as an assumption (Task 3b).
- **R10** (qty 50,000 against a 100–1,000 corpus) is now RED instead of being
  priced by averaging across quantities (Task 2).
- **R06, R11, R14** stay RED, correctly: illegible input, envelope violation,

## What these numbers are still not

A 22.2% GREEN rate here says the gate *can* reach GREEN on a corpus built to
allow it. It says nothing about whether any of those four prices is correct. The
corpus is invented. Pricing accuracy requires `scripts/backtest.ts` on a real
export — see [reports/k3-backtest.md](k3-backtest.md), where K3 is recorded as
**unmeasured**.
